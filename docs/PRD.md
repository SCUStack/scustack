# 川流课栈 产品需求文档

## 问题陈述
四川大学学生在查找、沉淀和复用课程资料的过程中，长期依赖群聊、网盘、个人文档、Git 仓库与零散外链。人文社科类资料通常通过 QQ 群、微信群或网盘临时传播，存在目录混乱、链接易失效、无版本记录的问题；理工科类资料虽更易托管在 Git 平台上，但 Git 使用门槛较高、国内访问体验不稳定，且针对 PDF、Word、PPT、图片、压缩包等二进制格式的资料，缺少适配学生使用场景的版本管理方式。

现有资料渠道还存在质量参差不齐、检索效率低、适用学期不明确、课程与学院归属混乱、贡献反馈缺失等问题。学生往往需要在多个群聊、多个网盘、多个仓库之间反复搜索，仍难以判断资料是否适配当前课程、任课教师或考试节点。

川流课栈要解决的核心问题是：让四川大学学生能够以低门槛、高效率、可信赖的方式，查找、贡献、评价和维护全学科课程资料。

## 解决方案
川流课栈是面向四川大学全学科的公益型课程资料共享平台。平台以「学院 - 课程 - 学期 - 资料分类」为核心目录体系，统一承载独家托管资料与外部资源链接，并围绕课程搭建资料检索、版本管理、评价纠错与场景化推荐能力。

平台采用文本代码类资料与二进制文档类资料的双轨版本管理方案：文本、代码、Markdown 等资料保留类 Git 的历史追踪与差异展示能力；PDF、Word、PPT、图片、压缩包等二进制资料，则以版本号、适用学期、更新说明、贡献记录、文件校验与质量评价为核心进行管理。

前端采用高信息密度信息流与结构化课程页结合的交互形式：首页用于发现热门资料、近期更新内容与校历驱动的推荐内容；课程页支持精确筛选资料分类、学期、格式、来源、评分与版本。平台适配电脑、平板、手机的响应式访问，并预留微信小程序的移植能力。平台全程无广告，以公益属性保障开放性、低门槛与长期可维护性。

## 用户故事
1. 作为一名四川大学学生，我希望能通过课程名称搜索课程资料，以便快速找到我所修课程的相关资源。
2. 作为一名四川大学学生，我希望能按学院、课程、学期、分类浏览资料，以便在不知道确切文件名的情况下也能定位到资源。
3. 作为一名四川大学学生，我希望能按学期筛选资料，以便避免使用过时的资源。
4. 作为一名四川大学学生，我希望在资料信息可查时，能看到其适配的教师或教学场景，以便判断是否与我所上的课程匹配。
5. 作为一名四川大学学生，我希望能看到资料分类（如课堂笔记、考试资料、作业、实验报告、代码、教材、复习提纲等），以便找到我需要的资料类型。
6. 作为一名四川大学学生，我希望能在线预览常见文档类型，以便在下载前判断资料是否有用。
7. 作为一名四川大学学生，我希望能直接下载平台托管的资料，以便不再依赖不稳定的群文件或易失效的网盘链接。
8. 作为一名四川大学学生，我希望外部链接与托管文件能展示在同一个课程页面中，以便通过一个入口获取全部课程资源。
9. 作为一名四川大学学生，我希望能看到资料的评分与反馈，以便优先选择高质量资源。
10. 作为一名四川大学学生，我希望能举报错误、过时、重复或不合规的资料，以便保障平台的可信度。
11. 作为一名四川大学学生，我希望能看到资料是否经过其他用户或维护者验证，以便判断对资料的信任程度。
12. 作为一名四川大学学生，我希望能关注或收藏课程，以便有新资料更新时收到通知。
13. 作为一名四川大学学生，我希望首页能推荐与当前校历节点相关的资料，以便在考试、项目截止或选课阶段提前发现有用的资源。
14. 作为一名四川大学学生，我希望移动端无需安装专门软件也能正常使用，以便在课堂、通勤或复习时随时访问资料。
15. 作为一名四川大学学生，我希望能对标题、描述、标签以及可提取的文档正文进行全文搜索，以便仅通过部分关键词也能找到资料。
16. 作为一名四川大学学生，我希望搜索结果能展示所属课程、学期、分类、评分、格式与来源，以便快速对比不同结果。
17. 作为一名四川大学学生，我希望能按相关度、更新时间、下载量、评分与学期对资料排序，以便匹配不同的搜索需求。
18. 作为一名贡献者，我希望上传课程资料时可填写结构化元数据，以便其他用户能找到并理解这份资料。
19. 作为一名贡献者，我希望能提交外部资源链接，以便当链接形式更合适时，无需重新上传已有优质资源。
20. 作为一名贡献者，我希望替换或修订资料时能添加更新说明，以便用户了解改动内容。
21. 作为一名贡献者，我希望我的贡献历史能被记录，以便有价值的贡献可追溯到贡献者。
22. 作为一名贡献者，我希望上传表单能引导我填写必填字段，以免误提交无法使用或描述不清的资源。
23. 作为一名贡献者，我希望能标注资料的适用学期、教师、课程与分类，以便平台正确归类资料。
24. 作为一名贡献者，我希望能对现有元数据提出修正建议，以便课程页面的信息能持续优化。
25. 作为一名维护者，我希望新提交的内容进入审核流程，以便管控垃圾内容、版权风险与低质量资源。
26. 作为一名维护者，我希望能对提交的资料执行通过、驳回、合并、要求修改等操作，以便管控平台内容质量。
27. 作为一名维护者，我希望平台能对相似文件与链接进行重复检测，以免课程页面内容冗余杂乱。
28. 作为一名维护者，我希望能为资料标记信任状态（如未验证、社区验证、维护者精选、存疑等），以便用户了解资料的可信程度。
29. 作为一名维护者，我希望能处理下架申请与版权投诉，以便平台合规运营。
30. 作为一名维护者，我希望能留存上传、编辑、举报、处理决策的审核日志，以便平台治理可审计。
31. 作为一名维护者，我希望能管理学院、课程、学期与分类，以便保持目录结构的一致性。
32. 作为一名维护者，我希望能合并重复课程或别名，以免用户在多个名称下分散查找资料。
33. 作为一名维护者，我希望能将优质资源在课程页与首页置顶推荐，以便学生更快找到可信资料。
34. 作为一名首次访问的用户，我希望无需学习 Git、也无需加入群聊就能搜索和浏览内容，以便平台上手门槛低、易使用。
35. 作为一名回访用户，我希望能从最近浏览的课程与保存的资源继续使用，以便重复学习的流程更高效。
36. 作为一名网络较慢或不稳定的用户，我希望页面加载高效，且下载前能看到文件大小与格式，以免进行不必要的下载。
37. 作为一名注重隐私的用户，我希望公开的贡献展示不会暴露不必要的个人信息，以便安全地参与贡献。
38. 作为一名平台运营者，我希望平台不设置任何广告位，以便清晰保持公益定位、保护用户信任。
39. 作为一名平台运营者，我希望能获取搜索无结果、热门课程、失效链接相关的数据分析，以便将维护精力聚焦于真实需求。
40. 作为一名未来的小程序用户，我希望相同的课程与资料模型可适配微信小程序，以便后续拓展移动端入口时无需重新设计产品。

## 实现决策
- 产品采用以课程为中心的信息架构，学院、课程、学期、资料分类为核心组织字段。
- 教师、教学班、考试类型、专业、校区、适用人群作为元数据字段，首版不设为强制顶层层级；原因是并非所有资源都有可靠的教师专属场景信息。
- 平台在同一资料模型下，同时支持托管文件与外部资源链接两种形式。
- 资料包含结构化元数据：标题、描述、所属课程、所属学院、学期、分类、格式、来源类型、标签、贡献者、创建时间、更新时间、版本、信任状态、质量信号。
- 文本与代码类资料支持面向文本的版本历史与差异友好存储。
- 二进制文档类资料支持版本化文件替换、更新说明、文件校验值、预览元数据，以及政策允许范围内的历史版本下载。
- 单份资料可包含多个版本；其中一个版本为当前推荐版本，其余旧版本在具备追溯价值时保持可见。
- 首版优先实现浏览、搜索、上传、审核、评分、举报与基础版本历史功能，暂不优先开发高级个性化推荐。
- 搜索功能结合结构化筛选，与元数据、可提取文档正文的全文索引能力；技术可行范围内实现全文检索。
- 首页发现模块采用高信息密度信息流模块，搭配近期更新、热门课程、考试季资源、关注课程更新等实用快捷入口。
- 课程页优先采用结构化列表、筛选、排序与精简元数据的呈现形式，而非营销化的展示风格。
- 校历驱动推荐初期采用与校历阶段绑定的规则驱动逻辑，待积累足够使用数据后，再向更智能的个性化方向演进。
- 用户贡献需保持低门槛，同时通过验证状态、内容审核、社区反馈、举报处理搭建分层信任体系。
- 审核模型需区分用户提交、公开可见、已验证、存疑、下架等不同状态。
- 平台需保持清晰的公益定位：无广告、无付费置顶、无商业排名。
- 响应式网页是前端核心载体；微信小程序支持通过 API 与数据模型兼容性预留，首版不强制实现。
- 系统底层可通过类 Git 能力支撑文本与代码的版本管理，但普通用户无需理解 Git 相关知识。
- 平台支持中文优先的界面与搜索体验，包括课程别名与常用简称的适配。

## 测试决策
- 测试需验证用户可见的行为与产品契约，而非实现细节。
- 目录浏览测试需在最高可用层级开展，验证学院、课程、学期、分类下能产出符合预期的资料列表。
- 搜索测试通过搜索 API 或页面级行为执行，覆盖关键词搜索、筛选、排序、空结果、别名、托管/链接混合结果等场景。
- 上传与提交流程通过外部可见的状态流转进行测试：草稿/已提交、审核中、已通过、已驳回、存疑、已移除。
- 版本管理测试方式为：分别创建并更新文本/代码类资料与二进制文档类资料，验证当前版本、历史记录、更新说明与用户侧元数据的正确性。
- 评分、纠错与举报流程作为用户交互场景测试，验证其会改变可见的综合质量信号或进入对应审核队列。
- 校历驱动推荐使用固定校历日期与规则用例进行测试，确保推荐结果具备确定性。
- 响应式前端表现通过视口级检查覆盖桌面、平板、移动端布局，重点关注密集列表、筛选控件与文本溢出问题。
- 访问与审核测试需验证：未通过或已移除的资料不对公众可见，同时授权维护者仍可查看必要的记录。
- 外部链接处理需测试失效链接、重复链接、来源标注与安全外跳逻辑。

## 不在范围内
- 首版不包含原生移动端应用。
- 首版不包含微信小程序实现，但数据模型与 API 设计不应阻碍后续小程序开发。
- 首版不包含全个性化的机器学习推荐功能。
- 实时协作文档编辑不在产品范围内。
- 替代学校官方教学系统不在产品范围内。
- 未经许可托管有版权的教材、付费课程资料或受限官方资料不在产品范围内。
- 打造教师评分或课程八卦类平台不在产品范围内。
- 面向普通用户的复杂 Git 工作流（如分支、拉取请求、冲突解决）不在产品范围内。
- 付费会员、广告与商业推广不在产品范围内。

## 补充说明
- MVP（最小可行产品）的核心价值承诺是：学生查找、信赖、贡献课程资料的效率，要高于通过群聊、网盘文件夹或零散 Git 仓库的方式。
- 务实的 MVP 功能边界为：结构化课程目录、资料详情页、托管文件与外部链接支持、基于元数据的上传、审核机制、基础全文搜索、评分、举报与简易版本历史。
- 最重要的产品风险是治理风险。若缺少审核、信任状态、举报与下架处理机制，平台会快速堆积垃圾内容、重复文件、过时资料或版权敏感内容。
- 第二大风险是过度开发。首版在核心的可查找性与信任机制得到验证前，不应试图实现完整的个性化、全平台一致体验或高级二进制差异对比功能。
- 产品表述应始终围绕课程、资料、版本、信任、贡献与公益共享展开。
